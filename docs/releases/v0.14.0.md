# MOOSEDev v0.14.0

v0.14.0 lets the component map change with the code: components can be retired, merged and renamed, a wrong link can be removed, and `mint` keeps code-to-component links current.

## Highlights

### Components can be retired, merged and renamed

A component used to stay `accepted` forever. After a large refactor, components that were too narrow could not be folded into broader ones, and every reader kept using them.

- **`retire_component`** retires a component with a rationale. It then leaves listings, dossiers, validation and `relations` targets.
- **`retire_component` with `into`** merges it into another component. Its `concerns`, `constrains` and `realizes` links and its covered paths move to the other component, which supersedes it. Other links are reported, not moved.
- **`rename_component`** changes a component's name in place. Its IRI and links are kept.

A merge widens every moved Constraint to all of the absorbing component's files, and a plain retire stops the component's Constraints being delivered. Call `retire_component` with `dry_run: true` first: it writes nothing and names the Constraints affected. A retire or merge cannot be undone with a tool; the graph file's git history is the way back.

`relate` and capture now refuse a new `concerns`, `constrains` or `realizes` link to a retired component, and name its successor.

### A link can be removed

The new `unrelate` tool is the inverse of `relate`. It removes one relationship and its stored inverse, and running it twice is harmless. It refuses lifecycle links (`supersedes`, `hasRationale` and their inverses), judgment links (`playsRole`, `hasCriticality`) and `realizes`; those change through their own tools.

### Constraints attached with `constrains` reach code

A Constraint attached to a component with `constrains` was never shown: the entity dossier, editor hover, the agent push and Stories followed only `concerns`. They now follow both. Constraints attached this way start appearing in dossiers after the upgrade.

### `mint` keeps component links current

`mint` used to keep whatever `realizes` link an entity already had. After a path moved to another component, a more specific component was declared, or a component was retired, the stored links were stale. `mint` now re-points each link to the component that covers the file now, and drops a link no component covers. The dry run lists every change. A hand-set `realizes` link that disagrees with path coverage is replaced the same way.

Moved code is also handled more completely: a re-homed entity no longer keeps a leftover inverse link to its old component.

## Upgrading

No graph or vector-store migration is needed. Existing stores open unchanged, and the engine is still MOOSE v0.29.0.

- **Mixed versions.** v0.13.0 and earlier ignore component status. If a teammate on an older version opens a graph where a component was retired, it reappears as current on their machine. A merged component has no paths or links left, so the effect is small; a plainly retired one applies again there. Upgrade everyone who shares the graph.
- **Review a mint dry run.** Run `moosedev index`, then `moosedev mint` without `--apply`, and check the `realizes` changes before you apply.
- **Scripts that read `mint` output.** The `summary:` line has two new fields at the end: `realizes-moved` and `realizes-dropped`.
- **Ontology.** `supersedes`, `isSupersededBy`, `hasRationale` and `isRationaleFor` now also apply to system components. Projects that pin their own copy of the ontology files keep working, but miss the check that a component is superseded only by a component.
